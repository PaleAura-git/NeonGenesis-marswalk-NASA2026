# Map exports (backend → frontend)

Static snapshot generated by `backend/scripts/export_for_map.py` (default settings: 3.3 km/h, 15°, 6 h).
Regenerate after any pipeline change:

```sh
cd backend && source venv/bin/activate
python scripts/export_for_map.py data/processed/demo_grid.tif sites.csv [speed_kmh=3.3] [max_slope=15] [hours=6]
```

## Live API (for sliders and rehearsal)

```sh
cd backend && source venv/bin/activate
python scripts/server.py
```

Serves on `http://127.0.0.1:8000`, which matches the Vite dev proxy:

- `GET /api/mission`: same as `mission.json`
- `POST /api/plan`: takes the `InitialPlanningRequest` from `frontend/src/types/planning.ts` and returns the same shape as `plan.json`
  - Uses `walkingSpeedMetersPerSecond` (max 0.917 = 3.3 km/h), `maxSlopeDegrees` (max 20), `totalDurationSeconds` minus `elapsedSeconds`, `includedStops[].observationSeconds`, and `reserveSeconds` as a minimum reserve
  - `blockedAreas` (polygons in local metres) triggers a rehearsal: each route gets a `rehearsal` list explaining what changed versus no block
  - Errors return HTTP 400 with `{"error": "..."}`
- `GET /data/slope.png`: the slope overlay
- Not used yet: `currentPosition`, `completedStopIds`, `priority`

| File | Contents |
|---|---|
| `mission.json` | Base, stops, bounds, slope layer and data sources, in the `GET /api/mission` shape (schema 1.1) |
| `plan.json` | Time-focused and conservative routes in the proposed `POST /api/plan` response shape |
| `slope.png` | 400 × 400 slope overlay (0–30°, transparent where no data), north-up, registered to `bounds` |
| `optical.png` | HiRISE orthomosaic of the demo box, 2000 × 2000 (2 m; source is 25 cm), north-up, same `bounds`: the optical base layer |
| `terrain.png` | Terrain classes, 400 × 400: sand (yellow), bedrock (grey), rough (rust), steep (purple); opacity = confidence |
| `thermal.png` | THEMIS night IR, 400 × 400 (source 100 m), inferno ramp: brighter = stays warm at night (rockier) |
| `classifier_metrics.json`, `route_validation.json` | Real validation numbers from the pipeline; also embedded in `mission.json` as `validation` and shown in the map's info panel |

Coordinates: local metres, x east, y north, origin (0, 0) at the Three Forks sample depot (18.4529° N, 77.4083° E).
East-west distances are corrected for latitude, so these are true ground metres. The PNGs are expected at `/data/<name>.png` (copy them to `frontend/public/data/`, or let the API serve them).

Terrain classes: a random forest predicts surface material (sand / bedrock / rough) from HiRISE slope, roughness,
brightness and texture plus THEMIS night IR (USGS controlled mosaic, 100 m; a relative proxy for thermal inertia). "Steep" is measured, not predicted (mean slope > 15°).
Training labels (`backend/labels/labels.csv`) were made from HiRISE image patches with AI assistance. Two team
members each labelled 30 different random patches blind (`backend/labels/check_labels*.csv`). Agreement on
material: 74% (17/23) and 57% (8/14), **68% combined (25/37)**. Most disagreements are sand vs bedrock (8 of 12).
The team's "steep" calls mostly measured 4-15°, which is why steep is taken from the DTM instead of the image. Spatial cross-validation accuracy is 67% (always guessing "sand" scores 53%).
The planner uses the classes as speed factors (sand ×0.85, rough ×0.8, *assumed*) and the conservative mode
also penalises low-confidence cells.

## Differences from the current frontend validator

`parseMission` only accepts synthetic data. To load these real files it needs:

1. `dataMode`: allow `"real"` (currently only `"synthetic"`).
2. `sources`: allow a non-empty array (each item: `layer`, `mission`, `instrument`, `resolution_m`, `file`, `source`, optional `note`).
3. `unverifiedGeographicReference` is replaced by `geographicReference` with `status: "verified"`.

`plan.json` adds these to the draft route fields:

- `observationTimeSeconds`, `reserveSeconds`, `energyWh`, `oxygenKg`
- `restTimeSeconds`, `restSpots`: a 5 min rest after every 30 min of walking, each with `position`, `durationSeconds`, `slopeDegrees`, `roughnessDegrees`
- `slopeLimitDegrees`, `steepestSectionDegrees` (steepest 10% of any 10 m cell on the route), `slopeWarning` (text when that exceeds the limit, else null)
- `stopAccess`: per stop `reached`, `reason`, `viewingPoint`, `distanceMeters`, `groundSlopeDegrees`. A stop whose own cell is over the limit is not reached; the route goes to `viewingPoint`
- `limitingResource`: `time`, `energy` or `oxygen`, whichever has the least spare at the tightest point
- `spareSeconds`: spare walk-back time per resource beyond its reserve (negative = no safe return)
- `reserveMarginSeconds`: the spare of the limiting resource
- `returnBoundary`: polygon (local metres) of the area you could still walk home from at the start, with all reserves
- `returnBoundaryCheckpoints`: the same polygon on leaving each stop (`when`, `polygon`); empty = head straight home
- `status: "infeasible"` means no safe return exists for this plan; `explanations[0]` says which resource runs short

## Data sources (all NASA missions; files from USGS Astrogeology, NASA's planetary mapping partner)

| Layer | Mission / instrument | Product |
|---|---|---|
| Elevation, slope, roughness | MRO HiRISE DTM, 1 m | `JEZ_hirise_soc_006_DTM_MOLAtopography_DeltaGeoid_1m` (Mars 2020 landing site products) |
| Optical | MRO HiRISE, 25 cm | `JEZ_hirise_soc_006_orthoMosaic_25cm` (`backend/scripts/make_ortho.py`) |
| Thermal | Mars Odyssey THEMIS night IR, 100 m | THEMIS Night IR Controlled Mosaic v2, 2018 (`backend/scripts/fetch_themis.py`) |
| Rover track | Mars 2020 Perseverance | NASA `M20_traverse.json` ("Where is Perseverance?"), used in `validate_routes.py` |
