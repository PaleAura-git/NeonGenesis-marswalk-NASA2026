# Map exports (backend → frontend)

Static snapshot generated by `backend/scripts/export_for_map.py` (default settings: 3.3 km/h, 15°, 6 h).
Regenerate after any pipeline change:

```sh
cd backend && source venv/bin/activate
python scripts/export_for_map.py data/processed/demo_grid.tif sites.csv [speed_kmh=3.3] [max_slope=15] [hours=6]
```

## Live API (for sliders and rehearsal)

```sh
cd backend && source venv/bin/activate
python scripts/server.py
```

Serves on `http://127.0.0.1:8000`, which matches the Vite dev proxy:

- `GET /api/mission`: same as `mission.json`
- `POST /api/plan`: takes the `InitialPlanningRequest` from `frontend/src/types/planning.ts` and returns the same shape as `plan.json`
  - Uses `walkingSpeedMetersPerSecond` (max 0.917 = 3.3 km/h), `maxSlopeDegrees` (max 20), `totalDurationSeconds` minus `elapsedSeconds`, `includedStops[].observationSeconds`, and `reserveSeconds` as a minimum reserve
  - `blockedAreas` (polygons in local metres) triggers a rehearsal: each route gets a `rehearsal` list explaining what changed versus no block
  - Errors return HTTP 400 with `{"error": "..."}`
- `GET /data/slope.png`: the slope overlay
- Not used yet: `currentPosition`, `completedStopIds`, `priority`

| File | Contents |
|---|---|
| `mission.json` | Base, stops, bounds, slope layer and data sources, in the `GET /api/mission` shape (schema 1.1) |
| `plan.json` | Time-focused and conservative routes in the proposed `POST /api/plan` response shape |
| `slope.png` | 400 × 400 slope overlay (0–30°, transparent where no data), north-up, registered to `bounds` |

Coordinates: local metres, x east, y north, origin (0, 0) at the Three Forks sample depot (18.4529° N, 77.4083° E).
East-west distances are corrected for latitude, so these are true ground metres. `slope.png` is expected at `/data/slope.png`.

## Differences from the current frontend validator

`parseMission` only accepts synthetic data. To load these real files it needs:

1. `dataMode`: allow `"real"` (currently only `"synthetic"`).
2. `sources`: allow a non-empty array (each item: `layer`, `mission`, `instrument`, `resolution_m`, `file`, `source`, optional `note`).
3. `unverifiedGeographicReference` is replaced by `geographicReference` with `status: "verified"`.

`plan.json` adds these to the draft route fields:

- `observationTimeSeconds`, `reserveSeconds`, `energyWh`, `oxygenKg`
- `limitingResource`: `time`, `energy` or `oxygen`, whichever has the least spare at the tightest point
- `spareSeconds`: spare walk-back time per resource beyond its reserve (negative = no safe return)
- `reserveMarginSeconds`: the spare of the limiting resource
- `returnBoundary`: polygon (local metres) of the area you could still walk home from at the start, with all reserves
- `returnBoundaryCheckpoints`: the same polygon on leaving each stop (`when`, `polygon`); empty = head straight home
- `status: "infeasible"` means no safe return exists for this plan; `explanations[0]` says which resource runs short
